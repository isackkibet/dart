7. Recommended Build Order

Following the blueprint's own module sequencing, the correct order to build out admin_web to full parity:

  • 1
    tsconfig.json + Firebase config wiring Add tsconfig.json with strict mode. Wire Firebase project credentials via .env.local. This unblocks all subsequent TypeScript and Firestore work.
  • 2
    Shared layout — sidebar + admin auth guard Update layout.tsx with a sidebar containing the six blueprint nav items. Add a Firebase Auth check that enforces an admin custom claim before rendering any page.
  • 3
    /dashboard — main overview Build the top-level dashboard page with nav cards linking to: Finance, Advertiser, Polls, Moderation, Live Sessions. Source: zip2.1.
  • 4
    /finance + /finance/payouts — monetisation module KPI grid reading creatorEarnings, riskReviews. Payout review queue reading walletPayouts with approve/hold actions. Source: zip2.5.
  • 5
    /advertiser + /polls — ads & polls module Ads KPI dashboard reading adRevenueShare and campaign collections. Polls analytics reading vote aggregates and fraud-hold flags. Source: zip2.6.
  • 6
    /moderation — content & user reports Moderation report queue reading user-submitted report documents. Required to pass Gate 5 (Step 2.8). Source: zip2.7.

8. Conclusion

apps/admin_web is at 0% feature completeness against the master blueprint. The branch is correctly named and positioned in the build sequence — admin dashboards are intentionally the last module per DEVELOPER_EXECUTION_MANUAL.md. But the full feature set remains to be built: six routes, eleven Firestore bindings, a shared auth-guarded layout, and TypeScript configuration are all outstanding.

One of seven QA gates currently passes (the build gate, since the empty scaffold compiles). The remaining six gates — spanning Step 2.1, 2.5, 2.6, and the final production gates 4 and 5 — will only pass once the blueprint pages and data connections are implemented in the order above.
