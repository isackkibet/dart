Prologue
Release Arc
00 Release Arc: YOHPAL LIVE 1.0J Baseline → RC2 Context
1.0J Baseline — Phases 1–7 Complete

YOHPAL LIVE 1.0J represented the completion of Blueprint Phases 1–7 (overall ~98%). The core feature set — immersive feed, zero-wait playback, engagement rail, creator profiles, ads, chat, comments, live discovery, context intelligence, and the full safety/minor-protection stack — was all in production. The app shipped on both Android and iOS with a 5-tab navigation shell.

The 49-Gap RC2 Audit

Prior to declaring the 1.0J release candidate, an internal code audit identified 49 implementation gaps against the full release specification. These gaps fell into five areas:

  • Creator Identity Block — missing onOpenProfile callback contract, missing 4 required ValueKeys, incorrect semantic labelling
  • Creator Library Categories — only 12 of 16 categories implemented; no owner-visibility rules; no access control on backend
  • Creator Video Grid — not a sliver widget; no hasMore/onLoadMore pagination; missing state variants and ValueKeys
  • No-Repeat Feed — no client-side exposure tracking; no VideoExposureRepository; FeedController did not send exclusion sets; backend had no canReturnVideo gate
  • Feed Category Parity — FeedCategory contained a dead trending value; FeedCategorySelector was iOS-only (not shared to Android build); trending branch was unreachable dead code
RC2 Scope

RC2 closed all 49 gaps across five directive areas (Parts II–III), added the full Physical Device & Cross-Device Certification Pack (Part V), and validated all existing 1.0J base release implementations against the spec. This document covers both the 1.0J baseline and the RC2 additions in full.

Scope boundary: Financial compliance (web-only writes, write-locked Firestore rules), YCIOS architecture, and Phase 8 (Controlled Pilot) planning are outside the scope of this report. Firestore and Storage rules are never deployed from this repository — the user manages and deploys rules directly.

02 Immersive Video Feed Screen Shipped
Architecture overview

VideoFeedScreen is a full-screen Scaffold with backgroundColor: Colors.black. The body is a Column with a top bar (Search + FeedCategorySelector + Live TV) above an Expanded PageView.builder that scrolls vertically through an infinite list of video items.

Feed data flow
  • VideoFeedController owns the raw video list and pagination (loadMore() triggers at index N−5)
  • AdsRepository.watchActiveCampaigns() streams active ad campaigns; AdsController.adForIndex() injects ads at configured positions
  • View timer fires after 3 s on a video; calls VideoInteractionController.recordViewOnce()
  • PageView.onPageChanged drives: preload (ZeroWaitPlaybackController), context update (ContextIntelligenceController), and diagnostics (PlaybackDiagnosticsRepository)
Gestures & controls
  • Double-tap → like via onDoubleTapLike
  • Swipe right → Navigator.pushNamed('/creator-profile') — requires horizontal velocity dominance and >200 px/s
  • Tap → toggle controls visibility; auto-hide after 4 s
  • Controls show swipe hint, VideoOverlayWidget, and VideoEngagementRailWidget
System UI configuration

On initState, SystemChrome.setEnabledSystemUIMode(SystemUiMode.edgeToEdge) and transparent status/nav bars make the feed truly full-bleed. On dispose, system UI is restored to SystemUiMode.manual with all overlays.

Feed switching

_switchFeed(String type) calls VideoFeedController.startSuggestedFeed() or startFollowingFeed(uid) depending on the selected FeedCategory. A dead else branch still calls startTrendingFeed() — this is unreachable since FeedCategory has only 2 values (RC2 fix). Dead Code

03 Zero-Wait Playback System Shipped — 1.0H
ZeroWaitPlaybackController — 4-tier preload architecture

Uses media_kit (libmpv backend) which provides software AVC/HEVC fallback for devices with broken hardware decoders (e.g. Unisoc c2.unisoc.avc.decoder). Each video is represented by an _MKBundle pairing a Player with a VideoController.

TierCountWhat's buffered
Active1Currently playing Player
Hot2–8 (CPU + network adaptive)Fully buffered Players around current index
Warm5–50 (network adaptive)Preview/start URLs pre-downloaded to disk cache via VideoMediaCache
ReadyRemainingVideo records provided by VideoFeedController
Network-adaptive sizing

SmartNetworkProfiler emits a NetworkClass stream. On each class change, hot-controller limit and warm-media count are recalculated:

  • WiFi / 5G: hot = CPU max (4–8), warm = 40–50
  • 4G: hot = 4–6, warm = 30
  • 3G: hot = 3–4, warm = 15
  • Constrained: hot = 2, warm = 5
  • None: hot = 2, warm = 0
Memory pressure & lifecycle
  • handleMemoryPressure() via WidgetsBindingObserver.didHaveMemoryPressure() — disposes all but the playing video and next preload
  • _disposeFarAway() culls controllers beyond keepDistance from current index automatically on each page change
  • Implements SessionScopedState.clearSession() — full teardown on auth sign-out
  • AdaptiveVideoUrlResolver.resolve() selects HLS HD on WiFi, HLS standard on cellular
04 Zero-Wait Video Player Widget Shipped
ZeroWaitVideoPlayer

A StatefulWidget that bridges ZeroWaitPlaybackController to the rendering surface. On construction it calls _warm() to either retrieve the pre-warmed VideoController from the controller or initiate warm-up.

  • _posSub — stream subscription on Player.stream.position; fires onFirstFrame callback on first non-zero position (first frame rendered)
  • _errorSub — stream subscription on Player.stream.error; fires onPlaybackError

  • isActive prop — widget calls play() when active, pause() when not; handles PageView reuse across indices via didUpdateWidget

19 Feed Eligibility Engine RC2 New
canReturnVideo() — eligibility logic
function canReturnVideo({ viewerId, creatorId, source, exposure? }): boolean {
  if (viewerId === creatorId) return true;                    // own video always eligible
  if (intentionalReplaySources.has(source)) return true;     // search, creator_profile, etc.
  if (!exposure) return true;                                 // never seen = eligible
  if (exposure.completedAt || exposure.maximumProgressPercent >= 80) return false;
  return exposure.automaticFeedEligible;
}
8 intentional-replay sources
search creator_profile shared saved liked history own_video swipe_back

Videos accessed via these sources are never suppressed by the no-repeat filter, because the viewer is explicitly choosing to see them.

Source union alignment

In viewer-video-exposure.ts, the source value "profile" was renamed to "creator_profile" to match the Flutter client's VideoExposureSource.creatorProfile. The old canAutomaticallyRecommendVideo function was removed entirely and replaced by the canonical canReturnVideo in feed-eligibility.ts.

20 No-Repeat Backend & Exposure Sync RC2 New
exposure-repository.ts

Firestore CRUD for viewerExposure/{viewerId}/videos/{videoId}. Writes exposure records with maximumProgressPercent, completedAt, automaticFeedEligible, and source. Used by get-feed.ts Callable to load server-side exposures and merge with client-sent exclusion lists.

exposure-sync-receipt.ts

The ExposureSyncReceipt interface is the cross-device sync proof artifact. Fields: syncedAt: Timestamp, deviceId: string, exposureCount: number, mergeConflicts: number. Returned by VideoExposureRepository.synchronize(). Required for RC2 cross-device certification gate (RC2-NR-XDEV-001).

get-feed.ts Callable

Merges client-sent excludedVideoIds with server-side exposure-repository records. Applies canReturnVideo gate to each candidate video. Returns FeedResponse with items and next cursor. Handles cursor-based pagination via decodeCursor.

A Firebase Storage trigger that fires when a video is uploaded. Handles: transcoding job dispatch, Firestore metadata write (title, ownerId, status), HLS URL population after transcoding completes. The trigger sets status: 'processing' on upload and status: 'live' after successful transcoding.

QA, Release & Certification
28 QA Release Identity RC2 New
qa_release_identity.dart

Reads compile-time constants from --dart-define flags. Fields:

  • buildSha — the git commit SHA stamped at build time
  • buildTimestamp — ISO-8601 build time
  • buildEnv — qa / staging / production
  • buildNumber

validateRc2() enforces the SHA format via regex ^[0-9a-f]{40}$ and throws a StateError if the build was not stamped. This method is called from the CrashlyticsVerificationService so that RC2 builds with missing SHAs fail visibly in QA telemetry rather than silently shipping an unverified candidate.

Crashlytics breadcrumbs

CrashlyticsVerificationService sets 4 custom keys on startup:

  • build_sha — from QaReleaseIdentity.buildSha
  • build_env — from QaReleaseIdentity.buildEnv
  • build_timestamp
  • build_number

These keys appear on every Crashlytics crash report, making it trivially easy to identify which build a crash came from during the physical device certification run.

Release Review Board — binding decision

The governance document at 21-governance/release-review-board-resolution.md requires sign-off from 6 boards (Architecture, Release, Security, AI Governance, Platform Operations, Executive Sponsor) and a binding decision of exactly one:

  • GO — all 24 gates pass; proceed to approved rollout tier
  • CONDITIONAL GO — gates pass with time-boxed remediation conditions; each condition requires owner, deadline, metric, monitoring method, rollback trigger
  • NO-GO — one or more critical gates failed; return to development

Approved rollout tiers: Internal QA only → Allow-listed users → Controlled percentage rollout → Wider rollout.
