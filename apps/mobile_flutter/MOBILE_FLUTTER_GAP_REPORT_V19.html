Finding 2 — _preloadAround() Uses Auth Header + Non-Adaptive Call (Critical)
2
video_feed_screen.dart — Auth Token Fetched Every Swipe · Always 360p · markBroken Unguarded
CRITICAL Code
Defect A — Firebase Auth token fetch on every swipe

_preloadAround() calls FirebaseAuth.instance.currentUser?.getIdToken() on every page swipe and passes the result as a Bearer header. Firebase Storage HLS download URLs embed their own ?token= query param — the Bearer header is not only unnecessary but causes HTTP 402 errors on HLS segment requests. The async token fetch also adds ~200 ms latency before the first warm call fires.

Defect B — Always calls non-adaptive preloadAround(urlFor)

The callback resolves every video to VideoModel.fromMap(id, data).hlsUrl, which always returns hlsLowUrl (360p) because VideoModel.fromMap() picks the lowest-latency URL regardless of network. Even after the adaptive controller is restored, this call site would still lock every device to 360p.

Defect C — markBroken() has no try/catch

VideoFeedRepository.markBroken() issues an unconditional Firestore update. The videos/{id} rule only allows updates when request.auth.uid == resource.data.userId. When a video owner watches their own video and the hardware decoder fails, markBroken() succeeds and permanently sets broken: true on that document. Non-owners get PERMISSION_DENIED but the unhandled exception surfaces as an unhandled future error. A try/catch is needed to silently drop both cases.

Diagnostic Side-Effect

The onFirstFrame diagnostic records networkType: 'unknown' hardcoded. Without the isOnWifi getter from the adaptive controller, the field can never be populated correctly.

Replace _preloadAround() with preloadAroundAdaptive() — no auth header Add try/catch to markBroken() in video_feed_repository.dart Wire isOnWifi into onFirstFrame networkType diagnostic
Finding 3 — Follow Button Never Toggles to "Following" (High)
3
Follow State Hardcoded false — No Live Stream in Rail Widget
HIGH Code
Defect A — _onFollow() always passes currentlyFollowing: false

In video_feed_screen.dart:104, _onFollow calls toggleFollow(currentlyFollowing: false, …) unconditionally. Every tap calls follow() — never unfollow() — regardless of the actual follow state. Tapping twice creates duplicate /follows/ documents.

Defect B — VideoEngagementRailWidget has no follow-state stream

The follow button is rendered from a const static list with hardcoded label 'Follow' and icon Icons.person_add_alt. There is no StreamBuilder on FollowRepository.watchIsFollowing() anywhere in the widget tree, so the button never changes appearance after a follow action.

FollowRepository.watchIsFollowing() already exists and returns Stream<bool> — it just needs wiring into the rail and the callback.

Fix
  • Wrap the follow button in VideoEngagementRailWidget in a StreamBuilder<bool> on FollowRepository.watchIsFollowing(followerUid, creatorUid)
  • When isFollowing == true: show Icons.person_remove, label 'Following', tint green
  • Pass the live isFollowing value down through the onFollow callback to _onFollow, then forward it to toggleFollow(currentlyFollowing: isFollowing)
StreamBuilder in VideoEngagementRailWidget Fix _onFollow currentlyFollowing param
Finding 4 — Following Feed Always Empty (High)
4
followingFeed() Queries followerIds — A Field That Is Never Written
HIGH Query Redesign Index

VideoFeedRepository.followingFeed() queries the videos collection with .where('followerIds', arrayContains: userId). No video document has a followerIds field — the query always returns zero results.

FollowRepository.follow() writes a document to /follows/{followerUid}_{creatorUid} and increments creatorProfiles/{uid}.followerCount. It never writes to any video document. The followerIds field is structurally absent from the data model.

Fix — Two-Step Query via /follows/ Collection

First fetch followed creator UIDs from /follows/ filtered by followerUid == userId, then stream videos where userId is in that set using whereIn (max 30 per batch). The existing firestore.indexes.json already contains a videos: userId + playbackReady + timestamp composite index which covers this query. For >30 followed creators, paginate in chunks of 30 and merge.

Redesign followingFeed() in video_feed_repository.dart
Finding 5 — YCIOS Workspace Assets PERMISSION_DENIED (High)
5
watchProjectAssets() Missing creatorId Filter — Firestore Rule Denies Query
HIGH Code Index

YciosRepository.watchProjectAssets(projectId) queries yciosAssets filtered only by projectId. The Firestore rule at firestore.rules:494 requires resource.data.creatorId == request.auth.uid on every read. Because the query does not include a where('creatorId', isEqualTo: uid) clause, Firestore cannot guarantee that all returned documents satisfy the rule and rejects the entire query with PERMISSION_DENIED — even for the project owner.

Compare with watchProjects(creatorId) and watchRenderJobs(creatorId) — both include the creatorId filter and work correctly.

Fix

Add a creatorId parameter to watchProjectAssets() and prepend a where('creatorId', isEqualTo: creatorId) clause. A new composite index on yciosAssets: creatorId + projectId + createdAt is required — it is not currently present in firestore/indexes/firestore.indexes.json. All call sites in YciosProjectDetailScreen must pass FirebaseAuth.instance.currentUser?.uid.

Add creatorId param to watchProjectAssets() in ycios_repository.dart Update call sites in YciosProjectDetailScreen Add yciosAssets: creatorId + projectId + createdAt index

Verdict
The platform is at 99% feature-complete (v18 baseline). Videos load and play in the Suggested and Trending feeds — the Zero-Wait engine is operational at the base level but the adaptive quality layer is not present, leaving every device at 360p regardless of network tier. The auth-token fetch in _preloadAround() adds latency on every swipe and risks 402 errors on HLS segments.

Three further high-severity issues exist independently: the Follow button never reflects state, the Following feed has a structural query flaw that guarantees zero results, and the YCIOS Workspace throws PERMISSION_DENIED on every project open due to a missing Firestore query constraint.

Recommended fix order (total ~2 h): ZeroWait controller (45 min) → _preloadAround + markBroken (15 min) → YCIOS creatorId filter (20 min) → Follow state stream (30 min) → followingFeed redesign (25 min) → AI secrets (15 min operator).
